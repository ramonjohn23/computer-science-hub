Database design

A good database is designed before it is built. The aim is to decide what data is needed, how it should be organised, and how the different parts are related.

Your level

The core ideas in this lesson apply to both SL and HL. Use the level selector to highlight the extension note.

🔬 Try this first

A school wants to store information about students, classes and teachers. What information should be stored? How could the school show which students attend which classes?

Possible answer

Separate STUDENT, CLASS and TEACHER entities. Give each entity a unique ID. Use a relationship or linking table to record student enrolments, because one student can attend several classes and each class can contain several students.

Big idea

Conceptual design explains what the database needs to represent. Logical design specifies tables and keys. Physical design explains how a particular DBMS stores and accesses the data.

A3.2.1 · Database schema

Three levels of schema

A schema describes how data is organised and how relationships are managed. Database design can be considered at conceptual, logical and physical levels.

Schema levelWhat it describesExample
ConceptualHigh-level entities, attributes and relationships. It does not focus on technical implementation details.Customers place orders.
LogicalDetailed structure: tables, fields, data types, primary keys, foreign keys and constraints. It is not tied to one specific DBMS.OrderDate has data type DATE; CustomerID is a foreign key.
PhysicalHow the logical design is implemented in a specific DBMS, including storage, indexes and partitions.Create an index on CustomerID to support faster searches or joins.

Entities

Attributes

  • ORDERS: OrderID, OrderDate

3 · Physical model

Physical schema – an example SQL implementation

This example uses SQL syntax commonly supported by relational DBMSs. Exact data types, auto-numbering syntax and index behaviour can vary between systems.

Physical detailImplementation choicePurpose
Primary keysINTEGER generated identifiersUnique row identification.
Foreign keysFOREIGN KEY constraintsReferential integrity between tables.
Data validationNOT NULL, UNIQUE and CHECKPrevent invalid or incomplete values.
IndexesIndexes on foreign-key columnsCan speed up joins and lookups.
CREATE TABLE CUSTOMER (
  CustomerID INTEGER PRIMARY KEY,
  CustomerName VARCHAR(100) NOT NULL,
  EmailAddress VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE PRODUCT (
  ProductID INTEGER PRIMARY KEY,
  ProductName VARCHAR(100) NOT NULL,
  Price DECIMAL(10,2) NOT NULL CHECK (Price >= 0)
);

CREATE TABLE ORDERS (
  OrderID INTEGER PRIMARY KEY,
  OrderDate DATE NOT NULL,
  CustomerID INTEGER NOT NULL,
  FOREIGN KEY (CustomerID) REFERENCES CUSTOMER(CustomerID)
);

CREATE TABLE ORDER_PRODUCT (
  OrderID INTEGER NOT NULL,
  ProductID INTEGER NOT NULL,
  Quantity INTEGER NOT NULL CHECK (Quantity > 0),
  PRIMARY KEY (OrderID, ProductID),
  FOREIGN KEY (OrderID) REFERENCES ORDERS(OrderID),
  FOREIGN KEY (ProductID) REFERENCES PRODUCT(ProductID)
);

CREATE INDEX idx_orders_customer
  ON ORDERS(CustomerID);

CREATE INDEX idx_order_product_product
  ON ORDER_PRODUCT(ProductID);
Why add indexes?

An index on ORDERS.CustomerID can help the DBMS find orders for a customer and support joins. An index on ORDER_PRODUCT.ProductID can help find orders containing a particular product. Indexes use additional storage and can make inserts or updates slightly slower because the index must also be maintained.

Design assumptions

The supplied conceptual information does not specify exact data types, field lengths, optionality or the DBMS. The logical and physical details above are therefore suitable teaching examples, not values explicitly stated in the original conceptual schema. The model assumes each order belongs to one customer, each order contains at least one product, and each product may appear in many orders.

Remember:

A conceptual schema is not detailed enough to build the actual database. It provides the high-level model from which a logical schema can be developed.

Logical schema tasks
  • Convert entities into detailed tables.
  • Specify data types and constraints for each field.
  • Establish primary and foreign keys.
  • Define relationships using the keys.
  • Normalise the database to reduce unnecessary redundancy.
Physical schema tasks

Choose DBMS-specific data types and storage settings, define indexes and decide whether large tables need partitioning. These choices can affect performance.

How the Three Levels Relate

Conceptual → Logical → Physical

Real-world meaning → Relational structure → Disk-level implementation

The level of detail increases from conceptual to physical.
How to understand the sequence
  • Conceptual: describes the real-world meaning and the information the organisation needs.
  • Logical: translates that meaning into a relational structure of tables, attributes and keys.
  • Physical: implements the logical structure using a specific DBMS and its storage features.

Data independence

This layered abstraction supports data independence: changes at one level should not unnecessarily affect the level above it.

  • Changes to physical storage should not affect logical structure.
  • Changes to logical structure should not affect real-world conceptual meaning.
HL extension note

Be prepared to interpret a detailed schema and explain how physical choices such as indexes can improve retrieval performance, while recognising that indexes also require storage and maintenance.

A3.2.2 · Entity-relationship diagrams

1. The different items within an ERD

An entity-relationship diagram (ERD) shows the entities (tables), attributes (fields) and relationships within a relational database. An ERD can be drawn at conceptual, logical or physical level.

Entity

An object that can have data stored about it. Entities are usually named using nouns and represented by rectangles. Examples: Student, Car, Player, Course, Product and MenuItem.

Key

An entity needs at least one key to identify its records. In a logical ERD, show the primary key and any foreign keys used to connect tables.

Relationship

The way entities interact. Relationships can be described using verbs, such as Student studies Course, Teacher teaches Course, or Menu contains MenuItems.

Attribute

Attributes describe the data stored about an entity. For a CAR entity, attributes might include Make, Model, EngineSize, FuelType and RegistrationNumber.

Relationships are read in one direction at a time

For example, a Menu contains MenuItems. A MenuItem does not necessarily belong to a Menu unless the system's rules specify that relationship. Always read and explain both directions separately.

2. Cardinality and modality

Cardinality describes how many instances of one entity can be associated with an instance of another entity.

One-to-one (1:1)

One record in entity A is associated with one record in entity B.

One-to-many (1:M)

One record in entity A can be associated with many records in entity B.

Many-to-many (M:N)

Many records in entity A can be associated with many records in entity B.

Modality describes whether participation in a relationship is optional or mandatory.

Notation (Crow's Foot)MeaningMinimum and maximum
○ —Optional one0..1
|| —Mandatory one1..1
○ with crow's footOptional many0..many
| with crow's footMandatory many1..many
Example: actor and theatre production

An actor may not have acted in a particular production, so participation for the actor can be optional. A menu must contain at least one menu item if that is a rule of the system, making the menu-to-menu-item participation mandatory.

3. Different ERD conventions

Different conventions represent the same database information in different visual ways. Three recognised styles are Chen, Crow's Foot and Barker.

Chen notation

  • Entity: rectangle
  • Attribute: oval
  • Relationship: diamond

Crow's Foot notation

  • Entities are boxes, often containing attributes
  • Lines connect related entities
  • Circles, bars and crow's feet show optionality and cardinality

Barker notation

  • Entities are commonly shown as rounded boxes
  • Attributes appear inside the entity box
  • Relationship line endings show one, many and optional participation

Visual guide: Chen notation

Chen notation: rectangle = entity, oval = attribute, diamond = relationship.

Visual guide: Crow's Foot relationship endings

Crow's Foot symbols: a circle means optional (zero); a bar means one; a crow's foot means many.

The exact visual appearance can vary slightly between diagramming tools. Focus on interpreting the minimum and maximum participation correctly.

4. Steps to construct an ERD

  1. Identify the level of ERD required. Decide whether the task asks for a conceptual, logical or physical model. This determines the amount of detail.
  2. Identify the entities. Add attributes and data types if the requested level requires them.
  3. Identify the relationships. Use verbs to describe how the entities interact.
  4. Identify cardinality. Decide whether each relationship is one-to-one, one-to-many or many-to-many.
  5. Identify modality. Decide whether participation is optional or mandatory at each end of the relationship.
Why construct an ERD?

ERDs provide a foundation for building a database. A clear model can be understood by other developers, supports maintenance and helps identify mistakes before development begins.

ERDs: model before building

An entity-relationship diagram (ERD) is a visual representation of entities, their attributes and the relationships between them.

Entity

A person, place, object or event about which data is stored. It is usually shown as a rectangle.

Attribute

A property that describes an entity, such as CustomerName or OrderDate.

Relationship

An association between entities, often shown as a labelled line or diamond.

Cardinality

Shows how many instances can be associated, such as 1:1, 1:M or M:N.

Example ERD: football club

The diagram shows that one team can have many players, while each player belongs to one team. Each team is managed by one manager, and each manager manages one team in this example.

Conceptual ERD: PLAYER — TEAM — MANAGER
Read the cardinality

PLAYER to TEAM is many-to-one: many players can play for one team. TEAM to MANAGER is one-to-one in this example. The rules of a real organisation determine whether these relationships are mandatory or optional.

Question 2 · Work experience database

A relational database, WORKEXPERIENCE, stores data about students and the companies where they complete work experience.

  • Students can complete multiple work experience placements but can only complete one placement at a time.
  • Students can complete more than one placement at the same company.
TableAttributes
STUDENTStudentID, FirstName, TelephoneNumber, UniversityName
PLACEMENTPlacementID, StudentID, CompanyID, StartDate, EndDate, Complete
COMPANYCompanyID, CompanyName, MaxStudentsPerPlacement

Task: Complete the ERD by adding the relationships and cardinalities. [2 marks]

Correct relationships · 2 marks
  1. STUDENT 1 → many PLACEMENT
  2. COMPANY 1 → many PLACEMENT

Each correct relationship is worth 1 mark in the supplied marking guidance.

Why? StudentID is a foreign key in PLACEMENT, so each placement belongs to one student, but one student can have multiple placement records over time. CompanyID is also a foreign key in PLACEMENT, so each placement is with one company, while a company can host many placements. The same student can therefore have several placements with the same company.

Important detail

“One placement at a time” is a business rule about overlapping dates. It does not change the one-to-many relationship between STUDENT and PLACEMENT; it is a constraint that would need to be enforced separately.

Why can CustomerID repeat in ORDERS?

A customer can place more than one order. CustomerID is unique in CUSTOMER, but it can repeat as a foreign key in ORDERS.

Example data types and constraints

FieldPossible typeConstraint / reason

Important distinction

A primary key must uniquely identify a row. A foreign key does not usually have to be unique: the same referenced record may be related to many rows in another table.

A3.2.5–6 · Normalisation

Normalise the database

Normalisation is the process of organising data into related tables to reduce unnecessary duplication and avoid insertion, update and deletion anomalies.

Start with an unnormalised table

OrderIDCustomerNameProducts
5001AmiraKeyboard, Mouse
5002BenMonitor
5003AmiraMouse, USB cable
What is wrong?

The Products field contains multiple values. Searching, updating or calculating totals for individual products becomes difficult. CustomerName is also repeated for Amira.

First Normal Form (1NF)

Each field contains a single, atomic value, and each record can be uniquely identified.

OrderIDCustomerNameProduct
5001AmiraKeyboard
5001AmiraMouse
5002BenMonitor
5003AmiraMouse
5003AmiraUSB cable

The table is in 1NF and every non-key attribute depends on the whole candidate key, not just part of a composite key. Separate order details from product details when they depend on different keys.

Exam memory aid

1NF: atomic values. 2NF: no partial dependency on part of a composite key. 3NF: no transitive dependency of non-key attributes on the key.

A3.2.7 · Denormalisation

When might a database be denormalised?

Denormalisation deliberately adds some duplicated data or combines tables to improve retrieval performance for particular workloads.

Possible benefit

Fewer joins may make frequently used queries faster.

Possible cost

Duplicated values need more storage and can become inconsistent if not updated everywhere.

Example

A reporting system might store CustomerName alongside an order summary so that a common report can be generated with fewer joins. The design must ensure that a name change is handled consistently.

Do not confuse the terms

Normalisation reduces unnecessary redundancy to improve integrity. Denormalisation intentionally introduces some redundancy when there is a justified performance or reporting need.

Compare the approaches

Normalised designDenormalised design
Data is split into related tables.Some data may be combined or repeated.
Usually reduces duplication and anomalies.May make some queries simpler or faster.
Often requires joins to retrieve related details.May reduce the number of joins.
Updates are generally easier to keep consistent.Updates may need to change several copies.
