Database design

A good database is designed before it is built. The aim is to decide what data is needed, how it should be organised, and how the different parts are related.

Your level

The core ideas in this lesson apply to both SL and HL. Use the level selector to highlight the extension note.

A school wants to store information about students, classes and teachers. What information should be stored? How could the school show which students attend which classes?

Possible answer

Separate STUDENT, CLASS and TEACHER entities. Give each entity a unique ID. Use a relationship or linking table to record student enrolments, because one student can attend several classes and each class can contain several students.

Big idea

Conceptual design explains what the database needs to represent. Logical design specifies tables and keys. Physical design explains how a particular DBMS stores and accesses the data.

A3.2.1 · Database schema

Three levels of schema

A schema describes how data is organised and how relationships are managed. Database design can be considered at conceptual, logical and physical levels.

Physical schema – an example SQL implementation

This example uses SQL syntax commonly supported by relational DBMSs. Exact data types, auto-numbering syntax and index behaviour can vary between systems.

CREATE TABLE CUSTOMER (
  CustomerID INTEGER PRIMARY KEY,
  CustomerName VARCHAR(100) NOT NULL,
  EmailAddress VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE PRODUCT (
  ProductID INTEGER PRIMARY KEY,
  ProductName VARCHAR(100) NOT NULL,
  Price DECIMAL(10,2) NOT NULL CHECK (Price >= 0)
);

CREATE TABLE ORDERS (
  OrderID INTEGER PRIMARY KEY,
  OrderDate DATE NOT NULL,
  CustomerID INTEGER NOT NULL,
  FOREIGN KEY (CustomerID) REFERENCES CUSTOMER(CustomerID)
);

CREATE TABLE ORDER_PRODUCT (
  OrderID INTEGER NOT NULL,
  ProductID INTEGER NOT NULL,
  Quantity INTEGER NOT NULL CHECK (Quantity > 0),
  PRIMARY KEY (OrderID, ProductID),
  FOREIGN KEY (OrderID) REFERENCES ORDERS(OrderID),
  FOREIGN KEY (ProductID) REFERENCES PRODUCT(ProductID)
);

CREATE INDEX idx_orders_customer
  ON ORDERS(CustomerID);

CREATE INDEX idx_order_product_product
  ON ORDER_PRODUCT(ProductID);
Why add indexes?

An index on ORDERS.CustomerID can help the DBMS find orders for a customer and support joins. An index on ORDER_PRODUCT.ProductID can help find orders containing a particular product. Indexes use additional storage and can make inserts or updates slightly slower because the index must also be maintained.

Design assumptions

The supplied conceptual information does not specify exact data types, field lengths, optionality or the DBMS. The logical and physical details above are therefore suitable teaching examples, not values explicitly stated in the original conceptual schema. The model assumes each order belongs to one customer, each order contains at least one product, and each product may appear in many orders.

Remember:

A conceptual schema is not detailed enough to build the actual database. It provides the high-level model from which a logical schema can be developed.

Logical schema tasks
  • Convert entities into detailed tables.
  • Specify data types and constraints for each field.
  • Establish primary and foreign keys.
  • Define relationships using the keys.
  • Normalise the database to reduce unnecessary redundancy.
Physical schema tasks

Choose DBMS-specific data types and storage settings, define indexes and decide whether large tables need partitioning. These choices can affect performance.

How the Three Levels Relate

Conceptual → Logical → Physical

Real-world meaning → Relational structure → Disk-level implementation

The level of detail increases from conceptual to physical.
How to understand the sequence
  • Conceptual: describes the real-world meaning and the information the organisation needs.
  • Logical: translates that meaning into a relational structure of tables, attributes and keys.
  • Physical: implements the logical structure using a specific DBMS and its storage features.

Data independence

This layered abstraction supports data independence: changes at one level should not unnecessarily affect the level above it.

  • Changes to physical storage should not affect logical structure.
  • Changes to logical structure should not affect real-world conceptual meaning.
HL extension note

Be prepared to interpret a detailed schema and explain how physical choices such as indexes can improve retrieval performance, while recognising that indexes also require storage and maintenance.

A3.2.2 · Entity-relationship diagrams

1. Significance of ERDs in Database Design

An entity-relationship diagram (ERD) is a visual model of entities and the relationships between them. ERDs act as a blueprint for an application-specific database before tables are created.

Clarify requirements

Translate user needs and business rules into a clear model of entities and relationships. This reduces misunderstanding about what the database must store.

Optimise structure

Reveal opportunities for normalisation, help ensure each piece of data is stored in the appropriate place, and reduce the risk of data anomalies.

Facilitate communication

Give analysts, developers, database administrators and other stakeholders a shared visual language to discuss and validate the design before implementation.

2. Modeling Relationships Between Entities

A relationship links two or more entity types to express how instances of those entities interact.

One-to-one (1:1)

Each instance of Entity A corresponds to at most one instance of Entity B.

Example: Each employee has one personnel record, and each personnel record belongs to one employee.

One-to-many (1:N)

One instance of Entity A can be related to multiple instances of Entity B. Each B instance is associated with one A instance.

Example: One customer can place many orders, but each order is placed by one customer.

Many-to-many (M:N)

Instances of Entity A can relate to multiple instances of Entity B, and vice versa. In a relational database, this is implemented using a junction (associative) entity.

Example: Students can enrol in multiple courses, and each course can have multiple students. An ENROLMENT entity links STUDENT and COURSE.

Remember

For a many-to-many relationship, the junction entity normally contains foreign keys referencing the primary keys of the two entities. These foreign keys can form a composite primary key, depending on the rules of the system.

3. Modality in ERDs

Modality refers to the minimum number of instances of one entity that can be associated with an instance of another entity. It shows whether participation at that end of a relationship is optional (0) or mandatory (1).

Cardinality describes the maximum number (one or many), while modality describes the minimum number (zero or one). Together, they describe the minimum and maximum participation at each end of a relationship.

Relationship endpoint symbols

Use the symbols below to identify the minimum and maximum number of related records at each end of a relationship.

Modality and cardinality symbols used at the ends of ERD relationship lines.
Symbol labelMeaningMinimum–maximum
OneExactly one instance1..1
One and only oneExactly one instance; participation is mandatory1..1
Zero or oneParticipation is optional; at most one instance0..1
ManyMore than one may be associatedMany
One or manyAt least one instance is required1..many
Zero or manyParticipation is optional; none or many instances0..many

Optional and mandatory participation

Optional relationship (0)

An entity instance may exist without being associated with an instance of the other entity.

Example: PATIENT and MEDICAL_RECORD

A new patient or a newborn child may not yet have any medical records. Therefore, a patient can have zero medical records: participation is optional on the medical-record side.

Mandatory relationship (1)

An entity instance must be associated with at least one instance of the other entity.

Example: CUSTOMER and ORDER

Every order in the e-commerce system must be associated with a customer. An order cannot exist without a customer, so the order's participation in this relationship is mandatory.

Do not confuse cardinality with modality

“Many” describes the maximum number of related instances. “Zero” or “one” describes the minimum. For example, 0..many means an entity can be related to no instances or to many instances; 1..many means at least one related instance is required.

4. Steps to construct an ERD

  1. Identify the level of ERD required. Decide whether the task asks for a conceptual, logical or physical model. This determines the amount of detail.
  2. Identify the entities. Add attributes and data types if the requested level requires them.
  3. Identify the relationships. Use verbs to describe how the entities interact.
  4. Identify cardinality. Decide whether each relationship is one-to-one, one-to-many or many-to-many.
  5. Identify modality. Decide whether participation is optional or mandatory at each end of the relationship.
Why construct an ERD?

ERDs provide a foundation for building a database. A clear model can be understood by other developers, supports maintenance and helps identify mistakes before development begins.

A3.2.3 · Data types used in relational databases

Choosing appropriate data types

Relational databases support different data types for numbers, text, dates, binary data and other structured information. Choosing the right type supports data integrity, query performance and storage efficiency.

The big idea

A data type defines what kind of value a field can store. For example, a date field should use DATE rather than ordinary text, and a price should use an exact numeric type such as DECIMAL.

A. Numeric types

Numeric types store whole numbers or numbers with fractional parts.

TypeWhat it storesExample / use
INTEGER / INTWhole numbers, positive or negative. Typically 4 bytes.5, -100; counts and identifiers.
SMALLINTWhole numbers with a smaller range; typically 2 bytes.Small counts or limited-range values.
BIGINTVery large whole numbers; typically 8 bytes.Very large counters or identifiers.
DECIMAL(p,s) / NUMERIC(p,s)Exact fractional numbers. p is total digits; s is digits after the decimal point.DECIMAL(5,2) can store 123.45. Suitable for money.
FLOAT / REAL / DOUBLE PRECISIONApproximate decimal values using floating-point representation.Scientific calculations; rounding differences may occur.

Why use DECIMAL for money?

DECIMAL stores an exact value to the defined precision. FLOAT stores an approximation, so calculations may produce small rounding errors.

B. Character and string types

These types store textual data such as names, addresses and descriptions.

CHAR(n)

A fixed-length string. It reserves the defined length and may pad shorter values with spaces.

Example: CHAR(10) storing 'dog' may be padded to the full length.

VARCHAR(n)

A variable-length string that stores up to n characters. It is more flexible for values of different lengths.

Example: VARCHAR(80) for a customer name.

When is CHAR useful?

Use CHAR when values have a fixed length, such as two-character country codes like PL or US.

C. Date and time types

TypeWhat it storesExample
DATEA calendar date.2025-05-26
TIMEA time of day.14:30:00
TIMESTAMPDate and time, often with fractional seconds. Time-zone support depends on the DBMS/type.A transaction date and time.

These types are useful for scheduling, recording events and tracking transactions.

D. Boolean type

BOOLEAN

Stores a logical value: TRUE or FALSE. It is useful for flags such as is_active or has_paid. Some systems represent these internally using values such as 1 and 0.

E. Binary types

TypeWhat it storesTypical use
BINARY(n)Fixed-length byte arrays.Fixed-size binary values.
VARBINARY(n)Variable-length byte arrays up to n bytes.Binary values with different lengths.
BLOBBinary Large Object; large raw binary content.Images, audio files and PDFs.

Binary values are not intended to be read as ordinary text. Some systems store large objects separately from the main table and keep a reference to them.

Summary of common data types

CategoryExample typesTypical use case
NumericINT, DECIMAL, FLOATCounting, measurement and financial values.
TextualCHAR, VARCHARNames, addresses and descriptions.
Date and timeDATE, TIME, TIMESTAMPScheduling and event logging.

Why data type consistency matters

Data integrity

Consistent types help prevent invalid values, such as ordinary text being entered into a numeric column.

Storage efficiency

Appropriate lengths and precision avoid unnecessary storage use. Fixed-length types can be useful when values are consistently sized.

Query performance

Database optimisers use type information. Mismatched types may require implicit conversions and can make queries slower.

Constraint enforcement

Data types support valid ranges, CHECK constraints and reliable arithmetic.

What can happen when the wrong type is chosen?

Potential problemExplanation
Precision lossUsing FLOAT for financial values may introduce rounding errors. DECIMAL is preferable when exact arithmetic is required.
Storage waste or truncationA VARCHAR length much larger than needed may be inefficient; a field that is too short may truncate or reject data.
Errors and conversion overheadInserting 123ABC into an INT field may fail. Implicit casts in joins or filters can reduce performance.
Index inefficiencyIndexes on wide or variable-length columns can consume more resources.
Loss of meaningStoring dates as TEXT loses built-in date validation and date calculations.
Key takeaway

Choosing the wrong data type can cause precision errors, wasted storage, slower queries and failures when data is inserted or manipulated. Choose a type that matches the meaning and expected values of the field.

A3.2.5–6 · Normalisation

Normalise the database

Normalisation is the process of organising data into related tables to reduce unnecessary duplication and avoid insertion, update and deletion anomalies.

Start with an unnormalised table

OrderIDCustomerNameProducts
5001AmiraKeyboard, Mouse
5002BenMonitor
5003AmiraMouse, USB cable
What is wrong?

The Products field contains multiple values. Searching, updating or calculating totals for individual products becomes difficult. CustomerName is also repeated for Amira.

First Normal Form (1NF)

Each field contains a single, atomic value, and each record can be uniquely identified.

A3.2.7 · Denormalisation

When might a database be denormalised?

Denormalisation deliberately adds some duplicated data or combines tables to improve retrieval performance for particular workloads.

Possible benefit

Fewer joins may make frequently used queries faster.

Possible cost

Duplicated values need more storage and can become inconsistent if not updated everywhere.

Example

A reporting system might store CustomerName alongside an order summary so that a common report can be generated with fewer joins. The design must ensure that a name change is handled consistently.

Do not confuse the terms

Normalisation reduces unnecessary redundancy to improve integrity. Denormalisation intentionally introduces some redundancy when there is a justified performance or reporting need.

Compare the approaches

Normalised designDenormalised design
Data is split into related tables.Some data may be combined or repeated.
Usually reduces duplication and anomalies.May make some queries simpler or faster.
